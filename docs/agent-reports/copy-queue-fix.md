## 2. Règle de la file (énoncée, testée : `C/tv/TransferQueue.kt` `QueueRules`)
Un seul envoi à la fois ; **le fichier en cours n'est jamais interrompu** ; un « Copier sur la TV et lire » passe **devant les simples copies en attente** (FIFO entre eux), parce que quelqu'un attend devant la TV ; un échec ne bloque pas les suivants, garde sa cause et se **réessaie** (en fin de file ; un « copier et lire » réessayé devient une simple copie : plus personne n'attend) ; après la mort du processus, l'élément en cours repasse en attente (reprise par le `.part` de la TV), rien de secret n'est écrit (jetons/PIN en mémoire seulement, relus par `PinStore` après redémarrage).

## 6. Risques
- `START_STICKY` : Android peut redémarrer le service de file en arrière-plan ; s'il refuse ensuite `UploadService`, la file se met en pause **et le dit** (pas d'échec) ; la notification de file reste alors affichée jusqu'à l'ouverture de l'app.
- Une file relue après redémarrage ne contient plus les accès « Ouvrir avec » non persistants : ces fichiers échouent avec « Accès au fichier perdu… » (choix de fichier SAF : accès persistant, ils repartent).
- `UploadService.start` lève désormais `Busy` quand un envoi tourne : `TvScreen`, `TvHub` (APK) l'affichent par leur `runCatching` ; `DlnaHandoff` protégé ici. Aucun appel restant sans protection (grep).
- La « Copier et lire » attend la fin de la copie en cours (règle « jamais interrompu ») : pour une copie longue devant, l'attente peut être longue ; elle est dite à l'écran (place + nom).
