# sonnet-w4-03-fix2 : second correctif de l'audit Opus (branche claude/sonnet-w4-03-fix2, depuis claude/sonnet-w4-03-fix)

Verdict d'audit traité : CORRECTIONS (2 bloquants, 2 majeurs, 2 mineurs). Toutes les décisions sont des fonctions pures de `core/lots/InstallKeyPolicy` (+ `InstallKeyGate`, `LazyKeyedApi`, `InstallKeyStore`), testées en JVM ; le module receiver ne fait que traduire ses exceptions Android.

1. **(bloquant) plantage d'`onCreate`** : `RentalHub.api()` est paresseux (`LazyKeyedApi`) : rien n'est construit à la mise en place du serveur ; une route de location (`/api/rental`, `/api/rental/install`, `/api/rental/sweep`) appelle `ensure` sous `runCatching` à chaque requête et répond **503 « coffre de clés indisponible »** en cas d'échec. Plus aucun appel du Keystore ne peut atteindre `TvService.onCreate`.
2. **(bloquant) perte de clé plain → keystore** : une clé est toujours LUE avec l'enveloppe nommée par son `wrap=` (`readers` : `plain` → PlainWrapper, `keystore` → `KeystoreWrapper.install()` sans sonde). Une clé plain trouvée alors que le Keystore marche est **migrée** (même graine, même installPub) : écriture SafeFile, relecture avec la nouvelle enveloppe, sinon remise atomique du fichier plain ; après relecture réussie le `.bak` plain est remplacé par une copie du nouveau fichier. `mayUseWrapper` (et son assertion fausse) est supprimé au profit de `readWith` / `migrateTo`.
3. **(majeur) erreurs avalées** : `KeystoreWrapper.unwrap` ne rend null que pour `AEADBadTagException`, alias absent (`containsAlias` = false) ou `KeyPermanentlyInvalidatedException` (`InstallKeyPolicy.unwrapIsLoss`, causes incluses) ; toute autre erreur est relancée. Contrat de `SecretWrapper.unwrap` mis à jour. `InstallKeyStore.loadOrCreate` lève `InstallKeyUnavailableException` sans toucher aucun fichier sur une erreur transitoire. Les fichiers `.unreadable-*` sont réessayés au premier chargement de chaque processus : une ancienne clé lisible redevient la clé (la clé générée entre-temps est gardée en `.superseded-<ms>`), les copies de la clé courante sont supprimées. Commentaire faux d'InstallKey.kt réécrit.
4. **(majeur) TV bloquée** : `InstallKeyGate` (horloge monotone injectée) espace les essais : 1 min pour les 3 premiers échecs, puis 1 h ; un seul journal par processus. `GET /api/activation` donne `installKeyProtection` = `keystore` / `plain` / `unavailable` / `pending` (admin.html : « coffre de clés indisponible (nouvel essai automatique) », « en préparation »). Compteurs dans `rental/install.key.retry` ; après **8 échecs sur au moins 3 démarrages**, régénération assumée (`regenerateAssumingLost`, note « illisible … », donc « demandez la réémission » une fois) ; l'ancien fichier reste en `.unreadable-*` et sera restauré si le Keystore revient.
5. **(mineur) attente du verrou** : `ensure` ne tient plus de verrou en chemin rapide, utilise `ReentrantLock.tryLock` (2 s pour les fils serveur, 30 s pour le préchauffage) et refuse d'essayer pendant le délai d'attente. `requestText` (écran d'activation, fil principal) passe par `installPubOrNull` qui ne bloque jamais le fil principal ; `/api/activation` par `protectionStatus` / `installIdOrEmpty`, non bloquants.
6. **(mineur)** `warming` = `AtomicBoolean.compareAndSet`.

Conservé : alias généré seulement s'il est absent, sonde sur son propre alias, note « illisible » une seule fois, « inconnue » dans l'admin pour un état inattendu. Ajout : une nouvelle clé dont l'enveloppe Keystore échoue à l'écriture est écrite en plain (déclaré) puis migrée au démarrage suivant, au lieu de rester en mémoire seulement ; une activation acceptée alors que le coffre est indisponible renvoie la note « réinstallez-la plus tard ».

## Tests
- `InstallKeyPolicyTest` (10 tests, tables) : pertes vs erreurs transitoires, lecteur/migration par étiquette, calendrier 1 min / 1 h avec horloge injectée, seuil de régénération, statut de protection, `InstallKeyGate` (fichier de compteurs sur plusieurs « démarrages »), `LazyKeyedApi` (rien construit à la mise en place, 503 puis reprise).
- `InstallKeyMigrationTest` (8 tests, enveloppes factices) : migration plain → keystore avec le même installPub, Keystore en panne pendant la migration (clé plain inchangée et lisible), fichier qui ne se relit pas (annulé), clé keystore jamais lue en plain + erreur transitoire sans modification de fichier, alias perdu, régénération assumée puis restauration de l'ancienne clé, copie illisible de la clé courante supprimée, repli plain d'une nouvelle clé puis migration.
- `InstallKeyTest` adapté (le modèle Flaky lève au lieu de rendre null ; panne longue = exception sans toucher aux fichiers).
- Résultats : nouveaux tests d'abord (30/30 verts : 8 + 10 + 12), puis `:core:test` complet : **2115 tests, 0 échec** (`DeviceTest.withoutDeviceReports501` passé cette fois) ; `:receiver:compileDebugKotlin` OK.

## Risques résiduels
- La restauration d'une ancienne clé après régénération remplace la clé générée entre-temps : les locations émises pour celle-ci devront être réémises (la note le dit ; au plus un basculement, la clé remplacée n'est jamais réessayée).
- La classification des exceptions Android (AEADBadTag, alias absent, KeyPermanentlyInvalidated, causes) n'est vérifiable que sur une vraie TV ; un Keystore qui répondrait `containsAlias=false` à tort serait pris pour une perte.
- `GET /api/activation/request` sans clé prête donne une demande sans `install=` (comportement antérieur).
- Pendant le préchauffage (quelques centaines de ms), les listes de locations du fil principal sont vides.

## À confirmer sur une vraie TV
Démarrage normal (keystore), migration d'une clé plain au redémarrage, comportement réel du Keystore GaiaOS en cas d'échec (exceptions levées), absence de plantage du service et réponse 503 avec le coffre indisponible.
