## Objectif
(1) **Une enveloppe de raison unique** : `C/sync/Reason.kt` (`ReasonCode` : code stable, HTTP, réessayable, message français ; `Reason.envelope(http, error, message, retryAfterMs)` qui **ajoute** `code`, `retryable`, `retryAfterMs` à tout JSON d'erreur de la TV sans retirer `error`/`message` ; en-tête `X-CB-Reason` ; `Reason.parse(http, headers, body)` côté téléphone avec repli `fromLegacy(http, error)` pour les TV anciennes). (2) **Le registre des refus** : `C/sync/RejectionLedger.kt` (32 dernières entrées, mémoire + fichier tournant, horodatage monotone + `bootId`, pair masqué, `X-CB-App` du pair, session) rempli par `ReceiverServer` à chaque refus, exposé dans `GET /api/transfer/state?id=` (`lastRejection`) et par une fonction `ledger.json()` que w19-06 servira dans `/api/sync/state`. (3) **Réessais bornés** : `C/sync/RetryPolicy.kt` pur (classes Transitoire / Refus / Identifiant / Session ; ≤ 12 essais ou ≤ 10 min cumulées ; courbe 2, 4, 8, 15, 30, 60 s ±25 % ; `retryAfterMs` prioritaire) branché dans `TransferClient.run` : une `IOException` sur `begin`/`finish` **n'est plus** une boucle sans borne ; après la borne ⇒ `Result.Paused(reason)` (TV absente : « En pause · reprise automatique au prochain contact », D-W19-12) ou `Result.Failed(GAVE_UP(dernier code))` (erreurs répétées). (4) **Lecture du registre après une coupure côté écriture** : sur `IOException` pendant `begin`/`chunk`/`finish`, `TransferClient` fait **une** requête `state(id)` ; si `lastRejection` est postérieur au début de la tentative (même `bootId`) et non réessayable ⇒ `Result.Failed(code)` immédiat. (5) **Vidage borné** côté TV : avant de fermer une connexion refusée sur `/api/transfer/chunk` et `/upload/`, lire et jeter le reste du corps **si ≤ 1 MiB** (généralise `bodyDrained` du 429), sinon fermer. (6) **Journal** : `ReceiverServer` appelle un `onRefusal: (RefusalLine) -> Unit` injecté (par défaut `println` à INFO au format `CB-REFUS route=… code=… http=… session=… peer=… app=… reason=…`) ; aucun secret (`Redact.scrub`).

## Pourquoi (preuves)
- `C/xfer/TransferClient.kt:141` : `catch (e: IOException) { onWaiting(...); sleep(retryWait(e)); continue }` sur `begin`, idem `:165` sur `finish` : **aucune borne** ; `retryDelayMs = 2000` (:108). Terrain R-17 : téléphone 1.2.39, TV 0.14.25, « Broken pipe » toutes les ≈ 25 s pendant > 30 min, rien côté TV.
- `C/tv/ReceiverServer.kt:570-575` : un refus sur `/upload/` et `/api/transfer/` ajoute `Connection: close` ; seul le 429 vide le corps (`bodyDrained`, `:1022-1040`) ⇒ sur un autre refus pendant qu'un bloc s'écrit, le téléphone reçoit « Broken pipe » **avant** la réponse.
- `ReceiverServer.kt:743-757` (`denied`), `:1200-1202` (`nameTaken`, déjà `"code":"NAME_TAKEN"`), `:1553` (`refuse`), `Folders.kt:157` (`err`) : formes d'erreur **hétérogènes**, aucune journalisation.
- `docs/BT-PLUG-AND-PLAY.md` « Jamais réessayé » : la règle existe pour la liaison (`CredentialGate`), pas pour le transfert.

## Étapes
1. **Rouge** : (a) `ReasonEnvelopeTest` : chaque code de la table § 3.1 a un HTTP, un drapeau réessayable et un français non vide ; `envelope()` conserve `error` et `message` tels quels et ajoute `code/retryable/retryAfterMs` ; `parse()` lit `code`, puis `X-CB-Reason`, puis `fromLegacy` (`409`+« name taken » ⇒ `NAME_TAKEN`, `403`+`trial` ⇒ `TRIAL_CLOSED`, `401`+« bad pin » ⇒ `AUTH_BAD_PIN`, `401`+« locked » ⇒ `AUTH_LOCKED` avec `retryAfter`, `429` ⇒ `BUSY(retryMs)`, `503`+« verifying » ⇒ `VERIFYING`, `503`+« volume removed » ⇒ `VOLUME_REMOVED`, `507` ⇒ `NO_SPACE`, `404`+« unknown transfer » ⇒ `SESSION_UNKNOWN`, `501` ⇒ `UNSUPPORTED`, autre ⇒ `INTERNAL`) ; `toString` d'une `Reason` ne contient jamais un PIN, un jeton ni une adresse complète (`Redact.scrub`) ; (b) `RejectionLedgerTest` : 32 entrées max, ordre, `bootId` stable par instance, fichier tournant relu au redémarrage, pair `ip:…x.y`/`bt:…ab` masqué, `json()` sans secret, `since(mono, bootId)` ; (c) `RetryPolicyTest` : classes, borne 12/10 min (horloge injectée), gigue bornée ±25 %, `retryAfterMs` prioritaire, `AUTH_LOCKED` ⇒ un essai à `retryAfterMs`, refus ⇒ 0 ; (d) `TransferClientBoundedRetryTest` : **R-17 rejoué** — un serveur qui ferme à chaque `begin` : le client s'arrête à ≤ 12 tentatives / ≤ 10 min simulées avec `Result.Paused(LINK_LOST)`, `onWaiting` dit « essai n/12 » ; une `ReceiverServer` réelle qui refuse `NAME_TAKEN` sur `chunk` en fermant : le client lit `lastRejection` et rend `Result.Failed(NAME_TAKEN)` **sans** second essai ; registre = 1 entrée ; `onRefusal` = 1 ligne sans secret ; un refus `BUSY` reste réessayé selon `retryMs` ; un refus sur `chunk` avec ≤ 1 MiB restant ⇒ corps vidé, réponse lue dans le corps (pas de « Broken pipe »).
2. `Reason` : `enum class ReasonCode(val http: Int, val retryable: Boolean, val fr: String)` + `object Reason { fun envelope(...): String ; fun parse(...): Reason ; fun fromLegacy(...) }` ; messages avec paramètres (`{n}`, `{volume}`, `{name}`) ; KDoc française.
3. `RejectionLedger` : `record(route, code, http, session, peerMasked, app, reason)`, `last(session)`, `since(mono, bootId)`, `json()`, persistance via `SafeFile` (W15) si un dossier est donné, sinon mémoire.
4. `RetryPolicy.decide(klass, attempt, elapsedMs, retryAfterMs, random): Decision(Wait(ms) | Pause(reason) | GiveUp(reason) | Stop)` ; `classify(reason)`.
5. `ReceiverServer` : point unique `json()` ⇒ `Reason.envelope` + en-tête `X-CB-Reason` ; registre + `onRefusal` dans `denied`, `nameTaken`, `refuse`, `spaceRefusal`, `transferChunk` 4xx/5xx, `upload` 4xx/5xx, `routeGuard` 403 ; vidage borné (`drainUpTo(1 MiB)`) **avant** `Connection: close` ; `transfers.stateJson` ⇒ `lastRejection`.
6. `TransferClient` : `RetryPolicy` sur `begin`/`finish`/`caps` ; `Result.Paused(reason)` nouveau (les appelants Android le traiteront en w19-09 ; en attendant il est mappé comme `Failed` par un `toLegacy()` pour ne rien casser) ; lecture `state(id)` après `IOException` ; `onWaiting("essai n/12 · <raison>")`.
7. **Vert** : porte ; `:core:test` complet ; les tests existants `CopyQueueServerTest`, `FluidPlaybackFixTest`, `CopyAndPlayHandoffServerTest`, `InFlightTest` restent verts (anciens champs conservés).

## Critères d'acceptation
- R-17 rejoué sur JVM : **rouge avant** (boucle > 12 tentatives en 10 min simulées, aucune raison), **vert après** ; sortie collée dans le rapport + ligne proposée pour `docs/REGRESSIONS.md` (R-17).
- Toute réponse d'erreur de `ReceiverServer` porte `code` + `X-CB-Reason` et conserve `error`/`message` (test qui parcourt la table des routes refusées).
- Aucun texte de refus en dur hors `Reason.kt` dans `C/sync`, `C/xfer` (test de source `lint`).
- Diff `ReceiverServer.kt` ≤ 120 lignes ; aucun changement de forme d'une réponse `200`.

## Cas limites
`retryAfterMs` absurde (> 30 s ⇒ borné) ; `bootId` différent ⇒ `lastRejection` ignoré ; registre plein ; fichier de registre corrompu ⇒ mémoire seule, rien n'est cru ; refus pendant `finish` ; deux lanes qui reçoivent la même coupure (une seule lecture du registre) ; TV sans `lastRejection` (ancienne) ⇒ `RetryPolicy` seul.

## À ne pas faire
Changer `v:"0.7"` ; toucher `/api/hello` (w19-02) ; retirer ou renommer un champ existant ; ajouter une route (w19-06) ; écrire dans `S/`, `R/` ; mettre un message français dans `TransferClient` (il vient de `Reason`).
