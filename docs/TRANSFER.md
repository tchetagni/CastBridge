# Transfert rapide : plusieurs voies, fichier découpé

Branche `claude/multipath-transfer`. Code : `android/core/src/main/kotlin/castbridge/core/xfer/` (pur, testé en JVM), routes `/api/transfer/*` dans `ReceiverServer`, branchement `UploadService` (téléphone). Banc : `tools/transfer-bench`.

## 1. Ce qu'on peut et ne peut pas accélérer
- Les modulations radio (OFDM/COFDM du Wi-Fi, du Bluetooth) vivent dans le micrologiciel des puces : Android ne les expose pas. **On agit au-dessus**, sur le transport : plusieurs connexions TCP/HTTP en parallèle, grands tampons, découpage en blocs, pipeline, choix et équilibrage des voies.
- Le débit d'une copie est borné par le **maillon le plus lent** : le Wi-Fi (un flux TCP seul en tire souvent moins que la capacité de la radio), puis **l'écriture disque de la TV** (clé exFAT mesurée entre 1,4 et 9,5 Mo/s ; port USB 2.0 ≈ 30 Mo/s en pratique, donc ce n'est pas le port). Le Bluetooth classique (RFCOMM, 0,1 à 0,25 Mo/s) n'apporte qu'un petit complément.
- Conséquence : si le disque est le goulot, **aucune** quantité de connexions ne fera mieux que sa vitesse d'écriture. Le moteur le mesure et le dit (ci-dessous). Rien dans ce document n'est promesse de débit : les seuls chiffres de débit sont ceux du banc, à lancer sur la vraie TV.

## 2. Principe
1. **Manifeste** : nom, taille, taille de bloc (1 Mio jusqu'à 64 Mio, 4 Mio jusqu'à 1 Gio, 8 Mio au-delà ; tranches de 256 Kio pour la voie lente). Un bloc est l'unité de travail, de vérification (SHA-256) et de reprise. L'identifiant du transfert = empreinte de (nom, taille, taille de bloc) : un téléphone relancé retrouve la copie partielle de la TV. Les décalages sont des `Long` (fichiers de plus de 4 Gio).
2. **TV** : un fichier **préalloué** (`.cbx/<id>.data` dans un dossier caché du volume, jamais listé ni compté comme fichier) écrit **en place** par `FileChannel` positionné, dans n'importe quel ordre, depuis plusieurs connexions. Tampon 256 Kio, aucune copie inutile ; la TV hache pendant qu'elle écrit. Un bloc ne compte que si son SHA-256 est celui annoncé par le téléphone. La carte des blocs et leurs empreintes sont sauvées à côté (`.state`), donc **la reprise survit à un redémarrage de l'app TV**.
3. **Fin** : `finish` relit tout le fichier sur le disque, recompare chaque bloc, vérifie l'empreinte de bout en bout (SHA-256 des empreintes de blocs, comparée à celle du téléphone), puis renomme (`.part`, même volume = atomique) et valide comme tout envoi (`commit`). Un bloc abîmé entre la réception et la relecture est oublié et renvoyé.
4. **Téléphone** : le fichier est lu par positions (`FileChannel`, `transferTo` sans copie vers la socket). L'empreinte d'un bloc est calculée la première fois qu'une voie en a besoin (pas de pré-lecture de tout le fichier), les empreintes déjà connues de la TV sont réutilisées à la reprise.

## 3. Protocole (additif ; mêmes authentifications que le reste : en-tête PIN ou jeton `TvCredential`, jamais dans une URL ni un journal)
| Route | Rôle |
|---|---|
| `GET /api/transfer/caps` | `{version, maxStreams, slice}` : une TV ancienne répond 404 → repli automatique sur l'envoi actuel (`ResumableUpload`) |
| `POST /api/transfer/begin?name&size&blockSize[&target]` | choisit le volume (mêmes règles que `/upload` : politique, quota, « 1 Go libre après le transfert »), préalloue, renvoie l'état (carte des blocs déjà là, vitesse d'écriture, flux max). 200 `{"done":true}` si le fichier est déjà complet |
| `PUT /api/transfer/chunk?id&idx[&slice]` + `X-CB-Sha256` (+ `X-CB-Enc: gzip`) | un bloc (ou une tranche de 256 Kio pour la voie lente). 200 ok / `already` ; 422 hachage faux ; 429 `busy` (contre-pression) ; 404 transfert inconnu ; 503 volume retiré ; 507 plus de place |
| `GET /api/transfer/state?id[&hashes=1]` | carte des blocs, `writeBps`, `queued`, `maxStreams`, `note` (voir §5) |
| `POST /api/transfer/finish?id&root` | vérification complète puis renommage ; 409 blocs manquants, 422 blocs corrompus (la carte mise à jour est renvoyée) |
| `POST /api/transfer/abort?id` | oublie la copie partielle |

Nettoyage : une copie non touchée depuis `orphanPartMaxAgeMs` (24 h, 7 jours sur clé USB) est supprimée, avec les `.part` classiques (`Storage.cleanOrphans`). Au plus 3 transferts simultanés, 6 flux d'écriture (`maxHttpThreads - 2`).

## 4. Voies (`Lane`) et ordonnanceur
- **`WifiLane`** : K connexions HTTP persistantes (sans poignée de main par bloc, tampon d'envoi 1 Mio, `TCP_NODELAY`, chien de garde contre une liaison figée). K s'adapte de 1 à 8 (`KController`) : on ajoute une connexion tant que le débit agrégé gagne au moins 8 %, on garde le meilleur K, on redescend quand la TV répond « occupé », on re-sonde de temps en temps. Compression `gzip` bloc par bloc seulement pour le texte et les archives non compressées (liste d'extensions) et seulement si le bloc gagne 10 % ; jamais pour les médias (mp4, mkv, mp3, jpg, zip…).
- **`BluetoothLane`** : une seule liaison lente, tranches de 256 Kio, en même temps que les autres. Le transport est du HTTP vers `/api/transfer` à travers un `SocketChannel` fourni par l'appelant : le tunnel d'API Bluetooth existant (`TunnelGateway`, port local de la passerelle) ou la liaison partagée de `claude/bt-tunnel-keepalive`. **Pas encore branchée dans l'app** (voir §7).
- **`WifiDirectLane`** : même voie sur l'adresse du propriétaire du groupe Wi-Fi Direct. **Expérimentale, désactivée** (`LaneSwitches.wifiDirect = false`) : aucun essai matériel. (Sans rapport avec le **Wi-Fi Direct automatique** R-14 : quand seul le Bluetooth relie le téléphone et la TV, la file monte le groupe et envoie par la voie Wi-Fi ordinaire sur 192.168.49.1 ; une seule radio à la fois, aucune agrégation. Voir `docs/agent-reports/auto-wifi-direct.md`.)
- **`UsbLane`** : interface seulement, **rien n'est simulé**. Piste de recherche : téléphone branché à la TV par câble USB-C. (a) Mode « accessoire » ou « hôte » Android : la TV de référence n'a que des ports USB-A 2.0 en hôte ; le téléphone devrait être l'« appareil » (gadget) et la TV l'hôte : il faut un pilote côté TV et une pile (MTP, RNDIS/Ethernet-over-USB, `adb`) ; (b) l'**Ethernet-over-USB** (RNDIS/NCM, « partage de connexion USB » côté téléphone) ferait apparaître un lien IP : la voie Wi-Fi marcherait telle quelle sur ce lien, sans nouveau code, si la TV l'accepte ; (c) USB 2.0 = ≈ 30 Mo/s réels, au-dessus de ce que la clé écrit : l'intérêt est la stabilité, pas la vitesse. À mesurer d'abord avec un câble et la TV réelle avant d'écrire une ligne.
- **Ordonnanceur** (`Scheduler`) : vol de travail (chaque ouvrier prend le prochain bloc manquant dès qu'il est libre : la voie rapide en fait plus) ; la voie lente prend par la **fin** de la file, les autres par le début (elles se rejoignent au milieu) ; en fin de transfert, un ouvrier rapide **envoie un doublon** du plus vieux bloc encore en vol (deux copies au plus), le premier arrivé gagne, l'autre est interrompu ; une voie qui échoue 3 fois de suite est **mise à l'écart** (1,5 s, puis ×2 jusqu'à 30 s) et ses blocs repartent sur les autres ; un bloc refusé plus de 4 fois (corrompu) arrête le transfert avec la raison ; si toutes les voies sont coupées, le transfert attend (comme l'envoi actuel) jusqu'à l'annulation.

## 5. Contre-pression et goulot
- La TV mesure **la vitesse réelle d'écriture** (temps passé dans `write`, moyenne glissante, donc elle suit une clé qui ralentit quand son cache est plein) et l'annonce (`writeBps`, `queued`). Elle n'accepte un bloc de plus que si les octets en vol ne dépassent pas ce que le disque absorbe en ≈ 3 s (au plus 6 blocs) ; sinon 429 `busy` et le téléphone ralentit (K baisse). On ne remplit donc pas la mémoire de la TV pour rien. Aucune hypothèse selon la version d'USB : seule la vitesse mesurée compte.
- Si le disque écrit à moins de 3 Mo/s, `state` porte une `note` en français : « Le disque de la TV écrit à 1,4 Mo/s : c'est lui qui limite la copie, pas le Wi-Fi. Un support plus rapide (clé USB plus rapide, autre port) accélérera la copie. » ; le téléphone l'affiche (`UploadService.notice`). **Non fait** : lire le type de port ou de clé (sysfs, `UsbManager`) pour l'ajouter au diagnostic : impossible à vérifier sans la TV.

## 6. Banc de mesure
`tools/transfer-bench/run.sh --tv http://IP:8765 --pin CODE --size 128M` (ou `CASTBRIDGE_PIN=… run.sh --tv …` pour que le code ne passe pas par l'historique du shell). Pour K = 1, 2, 4, 8, il mesure **deux fois** : **réseau seul** (la TV reçoit et vérifie les octets puis les jette : aucun disque) et **réseau + disque** (la vraie copie), plus l'envoi classique en référence, et écrit un tableau Mo/s. Il conclut lequel borne : si « réseau + disque » est nettement sous « réseau seul », c'est le disque de la TV. Les fichiers de test sont supprimés de la TV. Le Bluetooth ne se mesure pas ici (il faut le téléphone).
`--simulate` : sans TV, le vrai moteur contre le vrai serveur sur la boucle locale, avec des vitesses scriptées (par connexion, total Wi-Fi, disque, Bluetooth) : c'est un **modèle** pour voir les mécanismes (le gain de K=1 à 2, le palier du disque, un Bluetooth qui ne sert à rien quand le disque borne), **pas une mesure**. Exemple (3 Mo/s par connexion, 20 Mo/s Wi-Fi, disque 6 Mo/s, fichier 32 Mo) : K=1 ≈ 3,0 Mo/s, K=2 ≈ 5,9, K=4 ≈ 6,0, K=8 ≈ 5,6 (le disque borne).

**Mesures sur la vraie TV : aucune pour l'instant** (pas de matériel dans le cloud). À faire par le propriétaire.

## 7. Intégration et ce qui n'a pas été compilé
- `UploadService.runJob` : si le réglage « Transfert rapide (plusieurs voies) » est actif (case à cocher de l'onglet CastBridge TV, **activée par défaut**, préférence `castbridge_transfer`/`fast`) et **sans** « Lire pendant l'envoi » (les blocs n'arrivent pas dans l'ordre, la lecture progressive exige le flux séquentiel), le téléphone essaie `TransferClient` ; une TV sans le protocole (404 ou volume « dossier système ») reçoit l'envoi classique. La progression (pourcentage, durée, vitesse, notification) est alimentée par la même fonction que l'envoi classique.
- **Non compilé ici** (le plugin Android n'est pas téléchargeable dans le cloud) : `UploadService.kt`, `TvScreen.kt`, `FastTransfer.kt`. Le cœur (`:core`) est compilé et testé en JVM. À compiler et essayer sur le téléphone et la TV.
- **Pas fait** : brancher `BluetoothLane` dans l'app (il faut la liaison partagée de `claude/bt-tunnel-keepalive`, non fusionnée) ; volumes « dossier choisi par le sélecteur système » (SAF : refusés par `begin` avec 501, donc envoi classique) ; reprise **au milieu d'un bloc** pour la voie lente (une coupure Bluetooth renvoie le bloc en cours) ; si l'adresse de la TV change en cours de route, les connexions se rétablissent par redécouverte (callback `resolve`) mais l'en-tête `Host` garde l'ancienne valeur (sans effet pour le serveur).

## 9. Réglages de la copie et pourquoi (R-20, 2026-10-06)
Banc : `tools/transfer-bench/run.sh --simulate --size 348M --k 2,6 --conn 6M --wifi 24M --disk 16M [--low]` (modèle, pas une mesure ; affiche K final, blocs en vol au maximum et notifications ancienne / nouvelle).

| Réglage | Valeur | Pourquoi |
|---|---|---|
| Flux (`maxStreams`) | 6 par défaut ; `K auto` (`KController`) | banc 348 Mo, disque TV 16 Mo/s : K=6 16,57 Mo/s avec 24 Mo en vol, K auto 16,18 Mo/s avec 16 Mo en vol (K final 3) : plus de flux n'aident pas, le disque borne ; K=2 : 12,3 Mo/s (borné par la connexion) |
| Profil « ressources faibles » de la TV | lecture de `maxStreams` et de `blockSize` (OPTIONNEL) dans `/api/transfer/caps` ; `CopyTuning.streams/blockSize` | une TV 0.14.37 ne l'annonce pas : le téléphone garde sa politique ; une TV qui l'annonce ne reçoit jamais plus de flux ni de blocs plus gros (banc `--low` : 2 flux, 12,3 Mo/s, 8 Mo en vol au lieu de 24 Mo) |
| Blocs | 1 Mo (≤ 64 Mo), 4 Mo (≤ 1 Go, donc 87 blocs pour 348 Mo), 8 Mo au-delà ; la TV peut annoncer plus petit (plancher 1 Mo) | peu de requêtes, reprise fine ; un `blockSize` des caps ne peut que réduire (l'identifiant du transfert en dépend : un même profil donne la même reprise) |
| Mémoire côté téléphone | envoi sans copie (`transferTo`), tampon 1 Mo par flux ; compression : 2 blocs au plus en tas (`Semaphore`) | 6 flux x 8 Mo x 2 copies = 96 Mo en tas pour un fichier texte avant ; 2 blocs maintenant |
| Écriture côté TV | écriture directe 256 Ko, fsync PÉRIODIQUE tous les `syncEveryBytes` (64 Mo, x4 pendant une lecture, `PlaybackPriority`), sur un fil à part, jamais par bloc ; `force` final inchangé | la relecture finale ne trouve plus tout le fichier à vider d'un coup sur une clé USB ; l'écriture reste séquentielle sur FAT/exFAT (`ordered`) |
| Reprise | la TV rend les hachages des blocs reçus (`state?hashes=1`) : le téléphone ne relit et ne hache que les blocs manquants (test : 7 blocs sur 87) ; carte de blocs persistée par la TV (`.cbx/<id>.state`) | pas de re-hachage de 348 Mo à chaque reprise |
| Délais | connexion 5 s, lecture 15 s (60 s pour `finish`, qui relit le fichier) ; panne de liaison réessayée 2 s, 4 s, 8 s, 16 s puis 30 s, abandon rendu à la file après 10 min (`TvWait.GAVE_UP_TEXT` : la file attend la TV, R-19) ; un bloc qui échoue sur un flux attend 100 ms, 200 ms… 3 s | jamais de boucle serrée ni sans fin ; l'ordonnanceur garde `StuckDetector` (R-17) |
| Notification de la file | `NotificationGate` : republiée seulement si le texte ou le pourcentage change ; texte : au plus 1 par seconde, pourcentage seul : au plus 1 toutes les 2 s | avant : `notify(9)` toutes les 2 s même sans progrès ; copie arrêtée 60 s : 30 mises à jour avant, 1 maintenant ; copie qui avance : jamais plus qu'avant (banc : 15 / 15 pour 30 s) |
| Code 8 | 30 s, 1 min, puis 5 min par TV (`UntrustedBackoff`), un seul message ; la reprise ne contacte que les appareils qui exposent l'UUID CastBridge (`RecoveryCandidates`) | « reprise de HOCO Y12 Ultra: TvAbsent » (écouteurs) ; code 8 réessayé toutes les 13 s |
| Code demandé dans la boite | champ masqué « Code affiché sur la TV », bouton « Valider et envoyer » (une vérification, puis la copie part), code rangé par `PinStore`/`PinBook` ; file « Code requis » | parcours P-62 |

Non mesuré sur appareil : débit réel du Wi-Fi 2,4 GHz, coût CPU/batterie réel des notifications, effet du fsync périodique sur la clé USB de la TV, profil « ressources faibles » (fourni par la TV, autre chantier), source exacte de la boucle de 13 s du code 8 (non retrouvée dans le code : seule la reprise `recoverKnownTv` est bornée).
